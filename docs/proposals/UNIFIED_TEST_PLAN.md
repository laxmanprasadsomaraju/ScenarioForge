## (a) Deployment plan

Node 24 (`nvm use 24`). Run from a scratch copy or throwaway branch where `manifest.yml` is the approved variant (never commit that over the root; no script in the repo copies a variant, test-enforced). Build first: `npm ci && npm run frontend:install && npm run frontend:build`. Flags checked with `forge <cmd> --help` on 2026-11-12.

Never pass `-f/--no-verify` or `--approve`, and never omit `-e`. `forge deploy` without `-e` would use the default environment; always write `-e unified-test`.

**Phase 1 variable state:** `SF_STORAGE=enabled`, `SF_CRISIS=enabled`. `SF_AI`, `SF_USER_DAILY_CAP`, `SF_TWG`, `SF_REMEDIATION_WRITE` must be **unset**; confirm with `forge variables list -e unified-test` (they are never set on a new environment, so no `unset` command is expected).

**Flag names and values, from code** (`src/platform/storageFactory.ts`, `src/index.ts`, `src/twg/gateway.ts`): `SF_STORAGE`, `SF_CRISIS`, `SF_AI`, `SF_REMEDIATION_WRITE`, `SF_TWG` each switch on only for the exact string `enabled`; anything else or absent is off. `SF_USER_DAILY_CAP` is a decimal integer 50 to 300 (outside that range or invalid gives 50). Crisis rooms need `SF_STORAGE` and `SF_CRISIS` both `enabled`. Old `SF_ROVO_TEST_*` names have no effect.

**Redeploy after a variable change:** code reads `process.env` at invocation time, but whether Forge propagates a changed variable to already-deployed functions without a redeploy or `forge install --upgrade` is **unverified**. Plan: after each `variables set`, run a read-only test (for example History shows "storage available") and, only if it does not take effect, ask for a separate approval to redeploy. Setting variables before the first deploy is impossible (the environment must exist; setting after step 1 and before step 3 is allowed and avoids the question; recommended order: 1, 5a, 5b, 3, 4a, 4b).

## (b) Permanent schema commitments

Deploying makes these names and attributes permanent; they cannot be renamed or removed later. All three have the same declared shape, **no indexes**; every lookup is by key.

| Entity              | Attributes (exactly as declared)             | Stored                                                                                                                                     | Key prefixes                                                                                         | Limits and retention                                                                                                |
| ------------------- | -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `ai-governance`     | `version: integer`, `payload: string` (JSON) | AI usage ledger, settings, response cache. Written only when AI actions reach the governor (Phase 2)                                       | `ai-governance:settings`, `ai-governance:ledger:<period>`, `ai-cache:index`, `ai-cache:entry:<hash>` | Cache TTL 900 s, max 200 entries; ledger keeps current day per user                                                 |
| `rehearsal-history` | `version: integer`, `payload: string` (JSON) | Saved rehearsal runs and retests (`sfh1:`), remediation records (`remediation-item:`) and approval/audit records (`remediation-approval:`) | `sfh1:`, `remediation-item:`, `remediation-approval:`                                                | 50 runs per user, 90 days, 5 retests per run, value <= 200 KiB (Forge max 240 KiB), key <= 500 chars                |
| `crisis-room`       | `version: integer`, `payload: string` (JSON) | Crisis Room event logs (opaque participant ids, no names or emails)                                                                        | `sfc1:`                                                                                              | 400 events per room, 12 participants, 20 open invites, text 1000 chars, rationale 500, room <= 24 h, invite <= 24 h |

`remediation-item:` and `remediation-approval:` records are written only when `SF_REMEDIATION_WRITE=enabled`, which stays unset, so in this plan `rehearsal-history` holds only `sfh1:` keys. Is data pruned by the platform? Application-level pruning only; platform retention of Forge KVS and whether uninstall purges it are **unverified**.

Also permanent in practice: the environment name `unified-test` (whether an environment can be deleted: CLI offers `forge environments delete`, but it is not approved or tested here; permanence unverified).

## (d) Rollback

- Behaviour only: `forge variables unset -e unified-test SF_AI` (and `SF_USER_DAILY_CAP`) turns AI off again; same for `SF_CRISIS`. Needs approval.
- Remove the app: `forge uninstall -e unified-test -p Jira -s one-atlas-cegq.atlassian.net`, then `-p Confluence`. Leaves the environment idle with no installation. Needs approval.
- Stays permanent: the environment record, entity names and attributes, the deployed version history.
- Stored data after uninstall or in an idle environment: whether KVS data is purged or retained is **unverified**. Assume retained and treat test data as synthetic.
- `rovo-test`, `confluence-test`, `development`, staging, production: unaffected at every step; no merge, no root manifest change.
